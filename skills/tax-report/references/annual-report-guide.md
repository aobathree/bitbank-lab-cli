# 年間取引報告書（現物）との突合ガイド

`bitbank tax verify-report` が何と何を比べているかの参照資料。
**この文書に載っている数字は説明用の例で、実口座の値ではない。**

## 報告書の列と API の対応

| 報告書の列 | 突合キー | API 側の作り方 |
|---|---|---|
| 年始数量 | （比較しない） | 前年末残高。API からは当年ウィンドウで作れない |
| JPY建て年中購入数量 / 購入金額 | `buy_qty` / `buy_jpy` | 現物買約定の数量 / 約定代金 |
| JPY建て年中売却数量 / 売却金額 | `sell_qty` / `sell_jpy` | 現物売約定の数量 / 約定代金 |
| BTC建て年中購入・売却 | （比較しない） | 非 JPY クォート。CLI は P0 では計算しない → `unsupported` |
| 移入数量 | `deposit_qty` | 入庫（DONE のみ） |
| 移出数量 | `withdrawal_qty` | 出庫の `amount`。**手数料は含まない** |
| 支払手数料 | `fee` | 約定手数料 + 出庫手数料（当該通貨建て） |
| 貸出数量 / 返却数量 / 貸出損益 | （比較しない） | 貸暗号資産。API に相当データが無い → `unsupported` |
| 年末数量 | （比較しない） | 全履歴が要るので `bitbank tax reconcile` の担当 |

### JPY 行は暗号資産行の鏡像

暗号資産を売れば円が増えるので、報告書の JPY 行は次のようになる。

- JPY 行の「年中購入金額」= 暗号資産を売って**受け取った**円の合計
- JPY 行の「年中売却金額」= 暗号資産を買って**支払った**円の合計

したがって約定 1 件は base 側と quote 側の両方に計上される。
「BTC の買いが漏れている」ときは「JPY の売りも同額漏れる」ので、
差は必ず 2 か所に現れる。

## 突合の前に走る恒等式（`report_checks`）

報告書だけで閉じる関係式。API と比べる前にこれを検算して、
列の読み違い・行の欠落・編集済みファイルを弾く。

- **R1（行内）**
  `年末数量 = 年始数量 + 年中購入数量 − 年中売却数量 + 移入数量 − 移出数量 − 支払手数料`
- **R2（行間）**
  `JPY 行の年中購入金額 = Σ(暗号資産行の年中売却金額)`
  `JPY 行の年中売却金額 = Σ(暗号資産行の年中購入金額)`

いずれも実口座の報告書で成立を確認しているが、**取引所から確定仕様として
受領したものではない**。不成立はエラーにせず報告に留める。

## 差の診断

| diagnosis | 判定条件 | 典型的な原因 |
|---|---|---|
| `MATCH` | \|差\| ≤ 1e-4 | — |
| `FEE_ROUNDING` | 手数料で \|差\| ≤ 件数 × 5e-5 | API の手数料は小数第 4 位丸め値。報告書は丸め前合計の可能性が高い |
| `REPORT_EXCESS` | 報告書 > API | **販売所（即時売買）**。API に一切現れない。ほかに取込の打ち切り |
| `API_EXCESS` | API > 報告書 | 年分判定（JST）のズレ、重複排除の失敗、報告書の対象外（信用は別様式） |

### 手数料の許容幅を件数比例にする理由

API の手数料は 1 件ごとに小数第 4 位へ丸められている。報告書が丸め前合計なら、
差は最大でも「件数 × 半 ulp（5e-5）」までしか開かない。固定閾値にすると、
件数が増えるほど正常な丸め差を「取込漏れ」と誤診してしまう。

## 信用の年間取引報告書（別ファイル）

現物とは**別様式・別ファイル**。ペア（通貨）単位に 4 項目を持つ。

| 報告書の列 | 突合キー | API 側の作り方 |
|---|---|---|
| 年中信用取引損益（円） | `margin_pnl` | 決済レコードの `profit_loss` + `fee_amount_quote` |
| 支払手数料（円） | `margin_fee` / `margin_fee_occurred` | 精算ベース / 発生ベースの 2 通りを両方出す |
| 年末保有中買建玉 | （比較しない） | 全履歴が必要。法人向け項目（FAQ 3-1-13） |
| 年末保有中売建玉 | （比較しない） | 同上 |

### なぜ `profit_loss` に手数料を足し戻すのか

定義が違うため。

| | 定義 |
|---|---|
| 報告書「年中信用取引損益」 | 値幅損益 − 利息（**手数料は控除しない**） |
| API `profit_loss` | 値幅損益 − Σ手数料 − 利息 |

報告書は手数料を「支払手数料」列に分けて載せ、申告時にユーザーが**現物の取引手数料と
足して**国税庁計算書の「手数料等」欄へ入れる。国税庁計算書でも「信用・証拠金（差益/差損）」と
「手数料等」は別欄なので、この分け方に合わせる。

足し戻さずに比べると、差がまるごと手数料ぶん出る。所得の合計はどちらの分け方でも同じ
（収入 − 経費は同値）だが、報告書・計算書との**行の対応**が変わる。

### 手数料の合計基準（未確定）

報告書の「支払手数料」が精算ベース（bitbank は建て時の手数料を決済時に建て分と合算して
精算する）か、発生ベース（各約定日）かは資料から確定できていない。年をまたぐ建玉が
あると両者はずれるため、CLI は両方を出して**一致した方が基準**と分かるようにしている。

### 損益は個別法（FIFO）

信用は現物と違い、総平均法・移動平均法ではなく**個別法**で計算する（国税庁への照会で
「全て約定をベースに考える」と回答）。`--method` は信用の行に影響しない。

## よくある質問

**Q. 差がゼロにならない。バグ？**
まず `warnings` と `unsupported` を見る。差の原因は 1 つとは限らない。

1. **販売所（即時売買）** — 購入・売却に差が出る典型。API に一切現れないので、
   `--brokerage-csv`（売買履歴 CSV）を渡していなければまずそれを渡して再実行する。
   渡してもわずかに残る場合は、CSV に約定代金の列が無く `数量 × 指値価格` で
   算出していることによる誤差の可能性がある（数量は 8 桁で丸められている）
2. **履歴の打ち切り** — 「ページ上限で打ち切られています」が出ていれば差の解釈は無効
3. **未対応列** — BTC 建て・貸出に値があれば、その銘柄の差はこの分を含む
4. **年分境界（JST）・重複排除** — `API_EXCESS` 側の典型

これらを消してもなお購入・売却に `REPORT_EXCESS` が残るなら、その量が
「まだ取り込めていない販売所取引の規模」の目安になる。

**Q. 信用取引はどこ？**
現物の年間取引報告書には現れない（別様式）。現物の突合では信用イベントを集計から除外し、
除外件数を `warnings` に出す。信用は `--margin-csv` で別途突合する。

**Q. 信用で「年をまたぐ建玉があります」的な警告が出る**
`verify-report` は年ウィンドウで履歴を取るため、前年に建てた玉の決済だけが見えると
建玉トラッカーが整合違反として報告する。損益そのものは決済レコードの値を使うので
影響しないが、差が残る場合は `--max-pages` を上げて範囲を広げて確認する。

**Q. 年末数量が合っているか見たい**
`verify-report` は当年フローだけを見る。残高は全履歴が必要なので
`bitbank tax reconcile` を使う。
