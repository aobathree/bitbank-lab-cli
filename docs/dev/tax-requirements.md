## 1. 目的とプロダクト方針

### 1.1 何を作るか

bitbank口座の取引履歴を正規化し、**「bitbank口座における取引集計・税計算用参考データ」**を出力するCLI機能。

**「税務上の所得金額」とは呼ばない**（v2 §1.1）。理由: 総平均法・移動平均法は納税者が保有する同一銘柄**全体**（全取引所・全ウォレット横断）で計算するため。国税庁の計算例（FAQ 2-8）自体が複数取引所の合算である。

> **「単一取引所だから計算できない」とは書かない**（2026-07-27 修正）。限界が生じるのは**口座外に同一銘柄の保有・取引があるとき**であって、bitbank だけで完結している銘柄なら bitbank のデータが「全体」そのものなので譲渡原価は正しく出る。これは v2 §1.2 の表示ガード (a) アテステーション（`--attest`）が体現している条件そのもので、無条件に否定すると**自分のガードを否定し、主ターゲットである B 層（bitbank が主戦場）の数値まで無効に見せる**。

### 1.2 主ターゲット（営業ヒアリングより）

- **中口のマニュアル勢**（年間約定数〜10万件規模。超大口は自前システムを持つため対象外）
- **初心者**（利益が出たとき何をすればいいか分からない層）
- 個人が主。法人は対象外

**B層（上位botter・VIP/MM層）の規模感（Week 3 ヒアリング・取得済み）**:

| 項目 | 結果 | 設計への反映 |
|---|---|---|
| 年間約定件数の桁 | **年間約10万〜12万件**（ヒアリングでの**観測値**）。内訳の目安: トップHFT層は月間100万件程度の「**注文**」を出すが、**約定率は約1%**なので月間約定は約1万件 → 年間約12万件で観測値と整合する。年間10万件を処理できれば大多数の大口をカバー | NFRの10^5を裏付け。10^6は設計余裕として妥当 |
| 法人比率 | 大口のうち**法人は2〜3割**。多くは個人。国内ユーザー全体でも法人化は少ない | **観測事実**（大口の主体が個人であることの裏付け）。なお §1.3 の法人除外は**この比率を根拠にしていない** — 法人は期末時価評価が絡んで損益計算の前提そのものが変わるためのスコープ判断であり、比率が逆でも除外は変わらない |
| 税務処理の現状 | Cryptact等は**数万件規模でエラー**が出て高頻度botterにあまり使われない／税理士丸投げと自力計算が**半々**、ただし高頻度だと税理士も手作業困難で自作スクリプトを組む層が多い／単一取引所のみなら**年間取引報告書をそのまま**申告に使うケースもある | 「大量件数の正確処理」が差別化点。年間取引報告書で足りる層の存在はB案の前提と整合 |
| API外の収入イベント | 一部の超大口向けに**月単位のキャッシュバック**（手数料優遇）があるが対象者は極めて少数 | 自動取得のスコープ外とし、手動調整（ADJUSTMENT）で入力可能・免責に明記 |
| 複数アカウント運用 | サブアカ稼働は**20〜30人程度**と少数。全アカウント一括取得は不可（アカウントごとの個別APIキー）。この層は自前で対応できる人が多い | サブアカ対応はP1（§9 #7） |

**件数の読み方（重要）**: 年間10万〜12万件は**取引量上位 TOP10〜20 規模の「トップオブトップ」**であり、
業者に税務処理を委託しているような層。**主ターゲットは中口の裁量トレーダー**で、
**年間3万件を正確に処理できればかなり十分**。10^5 は上限側の設計値であって、
主ターゲットの実需はその 1/3 程度と見てよい。

> **性能判断への含意**: 非丸めの移動平均法は実用上限が**約5,000件**（[ADR-005](../adr/005-tax-exact-rational-arithmetic.md)）で、
> 主ターゲットの3万件にも届かない。「10^5 は上位層向けだから既定は非丸めでよい」とは言えず、
> 既定モードの判断（v2 付録D.6 との衝突）は主ターゲットの時点で顕在化する。

※ヒアリング時の「makerリベートは手数料計算とは別カラム・暗号資産ベースで数量調整」という情報は、
**生データ検証により否定**された（実際は `fee_amount_quote` のJPY建て負値。v2 付録E参照）。
この項目はヒアリングを根拠に使わないこと。

### 1.3 非目標（実装しない）

- 税額計算、確定申告の要否判定、申告書の作成
- 所得区分（事業所得／雑所得）の判定 — 警告のみ（v2 §2）
- 他社取引所・ウォレットの取込（A案。将来拡張のためスキーマのみ用意）
- 個別の税務相談に相当する出力

初心者向けの支援範囲は「**国税庁『暗号資産の計算書』互換の出力＋転記ガイド＋確定申告書等作成コーナー（e-Tax）への誘導**」まで。

## 2. データ源

### 2.1 API（本線）

[tax-evidence/ENDPOINTS.md](tax-evidence/ENDPOINTS.md) の棚卸しが正。**主要データ源は3つのみ**:

| エンドポイント | 用途 | 取得上の注意 |
|---|---|---|
| `GET /user/spot/trade_history` | 現物＋信用の全約定 | `pair` 省略で全ペア横断可。`count`最大1000＋`since`/`end`カーソル |
| `GET /user/deposit_history` | 入庫 | **`asset`省略＝cryptoのみ／`asset=jpy`明示＝fiat の2系統取得が必須** |
| `GET /user/withdrawal_history` | 出庫 | **`asset`必須**（全資産巡回が必要） |

補助: `GET /user/assets`（残高突合の基準・必須）、`GET /spot/pairs`（精度・手数料マスタ）、`GET /user/margin/positions`（年末未決済建玉の把握）。

**書き込み系（POST）は絶対に呼ばない。**

- ページ境界はタイムスタンプカーソルのため**同一ミリ秒で重複が返る** → `trade_id` / `uuid` での重複排除必須（実測で1件確認済み）
- レート制限: 逐次400ms間隔で429なし（実測）
- **レンディング・キャンペーン付与・エアドロップの履歴APIは存在しない**（docs全文精査で確認）。
  **販売所（即時売買）もAPIには現れない**が、こちらは UI CSV「売買履歴」で取得可能（§2.2）

### 2.2 UI CSV（**必須経路**。補助ではない）

**【2026-07-25 訂正】販売所（即時売買）の取引はAPIから一切取得できない**（注文ID照合で8件中0件一致）。`/user/spot/trade_history` が返すのは取引所（板）取引のみ。販売所取引はUI CSV「売買履歴」でのみ取得できるため、**UI CSV取込はAPI未導入ユーザー向けの補助経路ではなく、正確性のための必須経路**である。

販売所を使うユーザー（主ターゲットの一方である初心者に多いと想定される）について、API単独の取込は取得価額・損益を系統的に誤る。加えて**約定履歴CSVはAPIより高精度**（付録E.1）でもある。

CSVで取得できるもの: 注文履歴（税務では不要）／約定履歴／売買履歴（販売所。手数料列なし＝スプレッド内包）／入金履歴・出金履歴（**円のみ**）／信用貸付返済履歴(JPY)。

**デデュープ規則**: 信用の金利は約定履歴の `interest` を正とし、**「信用貸付返済履歴(JPY)」は取込まない**（二重計上防止）。

### 2.3 取得できないもの

レンディング利用料・キャンペーン付与・エアドロップは、履歴APIが存在しない（一部は入庫行に痕跡として現れる）。→ 残高突合で検出し、**手動調整（ADJUSTMENT）で補う**。

**【2026-07-25 訂正】**当初「積立とみられる」としていた残差は**販売所取引**であり、UI CSV「売買履歴」で取得可能だった（v2 付録E.3）。この口座に積立の証拠はない。ただし積立機能自体の履歴取得可否は未確認のため、残高突合による検出は引き続き必要。

### 2.4 API と UI CSV の統合優先順位

| 対象 | 正とするソース | 理由 |
|---|---|---|
| 取引所（板）の約定 | **API** | P-16（取引所が報告する値）。CSVの完全精度値は監査用に併存保持し、突合ログに差分を記録 |
| **販売所の売買** | **UI CSV「売買履歴」のみ** | APIに存在しない。重複の心配もない |
| 入出庫 | **API** | CSVは円のみ。暗号資産の入出庫はAPIのみ |
| 信用の金利 | **API 約定履歴の `interest`** | UI「信用貸付返済履歴(JPY)」は取込まない（二重計上防止） |

- 重複排除キー: 取引所約定は `trade_id`、販売所は注文ID。**両者のID空間は交差しない**ことを実データで確認済み（8件中0件一致）が、防御的に突合チェックを入れる
- API値とCSV値が同一 `trade_id` で乖離した場合は、API値を採用しつつ**警告**を出す（4桁丸めの差を超える乖離は異常）
- 未確定事項#1（年間取引報告書が丸め前・丸め後どちらの合計か）が解決したら、正とするソースを切り替えられる設計にすること

### 3.2 入出庫

| API | 正規化 | 規則 |
|---|---|---|
| `deposit_history[].amount` | `DEPOSIT` | 数量 +amount（手数料フィールドなし） |

## 4. 正規化イベントモデル

v2 §13を正とする。要点のみ:

- 全イベントに `ts_utc` と `ts_jst` を保存し、**年分は `ts_jst.year` で判定**（実データに12/28 JST = 12/27 UTC の例あり）
- `costbasis_provenance`（取得価額の由来）を取得系イベントに必須化: `PURCHASE` / `EXCHANGE_FMV` / `REWARD_FMV` / `ZERO_FORK` / `CARRYOVER` / `INHERITED_BOOK` / `GIFT_FMV` / `LOW_PRICE_SUM` / `DEEMED_5PCT` / `MANUAL`
- `account_id` を全イベントに持たせる（**サブアカウント対応の余地。優先度P1**）
- **シンボル名寄せは資産キー側で行い、ペア名は生値保持**。名寄せテーブルは `{matic→pol, rndr→render}` の2件のみ。**`mkr→sky` は1:24,000の換算転換のため名寄せ禁止**（手動マスタ）

## 5. 参考損益ガード（B案の核心）

以下**すべて**を満たす銘柄のみ参考損益を数値表示する。満たさない銘柄は**取引集計のみ**を出し、表示できない理由を明示する。

```text
(a) アテステーション: 「当年および取得価額の繰越に関係する過去年において、
    bitbank以外の取引所・ウォレット、および本ツールに取り込んでいない
    bitbankの他アカウント（サブアカウント含む）で同一銘柄の保有・取引がない」
    をユーザーが明示的に確認
(b) 未解決の入庫がない（入庫理由と取得価額の由来が解決済み）
(c) 前年末残高（数量・簿価）が確定している
(d) 残高突合: API全履歴から再構築した理論残高と /user/assets の実残高が
    資産ごとにダスト閾値（既定 1e-4）内で一致する
```

(d)が最重要。実口座で「残差 → **APIから取得できない販売所取引の発覚**」という実例があり（当初は積立と誤診したが、販売所CSVとの突合で全残差が説明された）、**自己申告と取込漏れを機械検証で裏取りする仕組み**として機能する。不一致時は残差の符号から原因候補（残差>0＝未取込の取得〔販売所買付・付与・移転〕、残差<0＝未取込の処分〔販売所売却・ダスト処分〕）を提示する。

出庫がある銘柄には「出庫先での売却・使用は本レポートに含まれない」警告を付す（計算自体は続行可）。

## 6. 計算エンジン要件

v2 §3を正とする。要点:

- **内部計算は Decimal・非丸め**。丸めは(i)出力層と(ii)国税庁Excel互換モードにのみ隔離
- 総平均法（既定）／移動平均法を**通貨ごと**に選択可能
- 不変条件テストを必須実装:
  - `I1: 期首簿価 + Σ取得価額 == Σ譲渡原価 + 期末簿価`（厳密一致）
  - `I2: 数量 >= 0、数量==0 のとき簿価==0`
  - `I3: 交換取引ごとに 支払側proceeds == 受取側cost`
- 国税庁Excel互換モード `NTA_SHEET_2025_12`（v2 付録D）: 総平均法は収入計ROUNDDOWN・経費計ROUNDUP、移動平均法は売却の都度 残高価額ROUNDUP
- 信用取引: 決済日の年分に `profit_loss`（ネット）を計上。**fee/interestを別途減算しない**。分解明細（売付価額/買付価額/金利/手数料）も併せて出力
- 手数料: 購入時→取得価額算入／売却時→必要経費。**負値（リベート）はJPY収入として計上**（P-04）

## 7. 非機能要件（NFR）

| 項目 | 要件 |
|---|---|
| スループット | 単一ユーザー・単年で **10^5 イベント**を実用時間で処理（設計余裕 10^6）。既存ツールが数万件でエラーになる事例があり、ここは差別化点 |
| 決定論性 | 同一入力→同一出力。同一タイムスタンプの約定は `trade_id` で安定ソート |
| 数値 | 全金額・数量は文字列→Decimal直パース。**float禁止**。`destination_tag` のみJSON number型なので注意 |
| 監査性 | 全イベントに source_ref・レート決定（ソース/時点/経路）・手動調整の履歴を残す |
| 冪等性 | 再取得・再計算で結果が変わらない。重複排除は `trade_id`/`uuid` |
| 堅牢性 | 未知のフィールド・未観測の形状（ショート建玉、fiat入庫行、CANCELED crypto出庫）で**黙って落ちない**。未知は警告して保留リストへ |
| セキュリティ | APIキーをログ・出力に含めない。GET のみ |

   - **実行条件**: 環境変数 `BITBANK_TAX_FIXTURES` が指す場所に実データがあればフル実行。

   - **期待値は fixture の SHA-256 で固定**: manifest と照合し、**欠落・内容相違は skip ではなく fail**。
     不一致時はどのファイルが一致しなかったかを列挙し、`gen-fixtures-manifest.ts` での再生成手順を示す
   - 検査項目:
   - `trade_id`/`uuid` 重複排除後の件数一致
   - 現物全行で `fee_amount_quote == fee_occurred_amount_quote`
   - 信用 `profit_loss` の検算（**完全精度の手数料を使えば誤差ゼロ**で再現。丸め値使用時のみ ±0.001円許容）
   - フィールド型スナップショット（API仕様変更の検出）
3. **残高突合テスト**: 理論残高 vs `/user/assets` を資産ごとに検証（ガード(d)の実装そのもの）
4. **Excel互換テスト**: `NTA_SHEET_2025_12` モードの出力を国税庁シートと突合（許容 ±1円/銘柄・年）
5. **性能テスト**: 10万件の合成データで所要時間・メモリを計測

## 10. 実装順序（推奨）

1. **P0**: 正規化スキーマ＋APIインポータ（3エンドポイント＋2系統取得＋重複排除）＋fixtures回帰テスト
2. **P0**: 残高再構築＆突合（ガード(d)）— `reconcile.ts` を製品コードへ昇格。原型は
   **独立実装との突合で全資産の残差一致を確認済みの検証済みオラクル**なので、次の手順で移す:
   1. `scripts/dev/tax/reconcile.ts` として取り込む（済。ローカル絶対パスは
      `BITBANK_TAX_FIXTURES` へ置換。**原型は削除せず恒久的に保全する**）
   2. `cli/tax/reconcile/rebuild.ts`（イベント列 → 資産別理論残高。出庫は `amount + fee` で減算）と
      `compare.ts`（`/user/assets` と突合・ダスト閾値・残差の符号診断）に分割
   3. Result パターン化（`throw` を除去）し、数値は `cli/tax/ratio.ts`（ADR-005）へ統一
   4. **原型と製品コードの結果一致を skip ゲート付きの恒久テストにする**（一度きりの確認にしない。
      fixture がある環境では常に差分検証が走る）
   5. `guard/reference-pnl.ts` からガード(d) として呼ぶ
   - **テストは「判定」ではなく「検出」にする**: 資産ごとの残差がダスト閾値内なら OK、
     そうでなければ**未追跡フローありとして残差の量と符号を報告**する（fail にしない）。
     「全資産で残差ゼロ」を期待すると実データでは必ず落ちる（**販売所取引が API に現れない**ため。
     [tax-evidence/BALANCE_RECONCILIATION.md](tax-evidence/BALANCE_RECONCILIATION.md) 結論1・2）
   - **`残差H2 − 残差H1 = −出庫fee合計` を検証に使わない**。H1/H2 の定義上の恒等式で
     全資産で成立するため証拠価値がない。識別しているのは「clean な資産で H1 だけが厳密ゼロ」という非対称性
3. **P0**: 平均法エンジン（総平均法／移動平均法・**厳密値保持／丸めは境界で1回**（v2 付録F・ADR-005）・
   不変条件テスト）＋税務ゴールデンケース
4. **P0**: 参考損益ガード(a)〜(d)＋レポート出力（免責文言はv2 §1.3／§9／§10／§12から転記）
5. **P1**: 国税庁計算書互換出力（`NTA_SHEET_2025_12`）
6. **P0**: UI CSV取込経路（販売所「売買履歴」＋約定履歴。完全精度・デデュープ規則）※販売所がAPI非対応のため P1 から昇格
7. **P1**: 手動調整（ADJUSTMENT）インターフェース＋監査ログ
8. **P2**: サブアカウントのマージ取込、`TRADE_EXCHANGE`（過年度BTC建てペア）
