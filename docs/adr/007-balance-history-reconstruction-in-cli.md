# ADR-007: 残高推移の再構築を CLI で行い、数値は倍精度で扱う

## ステータス

Accepted（2026-08-10）

## コンテキスト

`portfolio` skill の「JPY 建て資産推移」は **「現在の保有量 × 過去の価格」** で描かれていた。
入出金も売買も反映しないため、積み立てている口座では実残高から大きく乖離する。実機確認 #14 の
追試で、口座の持ち主が「資産が半減した」と誤認しかけた。

正しい実装は姉妹リポ `bitbankinc/bitbank-lab-mcp`（`src/handlers/portfolio/calc.ts`・`fetch.ts`）に
既にある: **現在の残高から約定・入出金を逆順に巻き戻して各時点の保有を復元し、その日の始値で
評価する**。設計を新たに起こす必要はなく、論点は「どこに置くか」と「どう数えるか」の 2 つ。

判断が必要になった点:

1. 復元ロジックは分析ロジックか（[ADR-002](002-no-analysis-logic-in-cli.md) は CLI に分析ロジックを
   持たないと定めている）
2. 数値表現。[ADR-005](005-tax-exact-rational-arithmetic.md) は税務経路に厳密有理数を要求する。
   移植元は `Number`（`calc.ts` に `Number(` が 33 箇所）
3. 履歴が取り切れなかったときの扱い。**再構築は入出金が 1 件欠けただけで静かに狂う**

## 決定

1. **復元ロジックを CLI に置く**（`cli/portfolio/`、コマンドは private の `balance-history`）。
   ADR-002 の 3 つ目の例外とする（既存は paper と [ADR-004](004-tax-logic-in-cli-exception.md) の tax）。
2. **数値は `Number`（IEEE754 倍精度）で扱う**。ADR-005 の厳密有理数は税務経路に限った規約とし、
   ここへは広げない。丸めは出力境界で 1 回だけ（円単位）行う。
3. **打ち切りは黙って通さない**。ページャは「短いページ = 最終ページ」で止めず（`cli/paginate.ts`）、
   打ち切ったら `Result.partial` / `meta.truncated` に加えて **レポート本体の
   `completeness` / `warnings` にも出す**。ただし tax の参考損益ガードのように
   **出力自体をブロックはしない**。
4. **前提の注記（`note` / `assumptions`）を出力に同梱する**。移植元の `PERFORMANCE_NOTE` 相当。
5. **移植元を各ファイルの冒頭コメントに明記する**。CLAUDE.md は「MCP は別リポ。直接 import しない」
   と定めているため、同じロジックが 2 リポジトリに存在する状態は避けられない。

## 理由

### なぜ CLI に置くのか（ADR-002 の例外）

ADR-002 が CLI から締め出したのは「**モデルが生データから再現できる**指標計算・パターン検出・
スコアリング」である。残高推移の再構築はそこに当てはまらない:

- **生データを渡しても復元できない。** 復元には約定・入庫・出庫・現在残高・1day 足・現在価格の
  6 系統を突き合わせ、**手数料の建て（base / quote）と符号を約定 1 件ごとに正しく戻す**必要がある。
  モデルに「巻き戻して」と指示して数千件を暗算させる形は、誤差ではなく誤りを生む
- **間違いが静かである。** 巻き戻しの符号を 1 つ間違えても系列は滑らかなままで、読み手には
  正しく見える。実機確認 #14 の誤認はまさにこの形で起きた
- **前提の同梱が要る。** 「復元値であって当時のスナップショットではない」を skill 側の記述に
  委ねると、書き忘れた瞬間に誤読が復活する。データに同梱して初めて剥がれない

一方で**判断は出さない**。増減の良し悪し・リバランスの要否は返さず、時系列と内訳と前提だけを返す。
ADR-002 の「MCP = 結論を渡す / CLI = 生データを渡す」の線はここで保たれている。

### なぜ `Number` でよいのか（ADR-005 を広げない）

ADR-005 が厳密有理数を要求した理由は**精度ではなく「丸めの適用回数と適用対象」**である
（同 ADR「問題の本質は精度ではなく…」節）。税務では ①不変条件 I1 の厳密一致、②国税庁 Excel 互換
モードの丸め境界の再現、という **丸めが意味を持つ要件**があり、桁を増やしても解決しない。

残高推移にはその 2 つが無い:

- **丸めは出力境界の 1 回だけ**（円単位）。中間で丸め直す箇所が無いので、ADR-005 の中核原則
  「丸めは厳密値に 1 回だけ」は倍精度のままでも守られる
- **成立させるべき厳密な不変条件が無い。** 出力は表示・分析用の時系列であって、申告書へ転記する
  確定値ではない
- **誤差の桁が丸め単位より遥かに小さい。** 倍精度の相対誤差は約 2.2e-16。数量の加減算を n 回
  重ねても誤差は概ね n·ε のオーダーで、1 万件の巻き戻しでも相対 1e-12 程度。評価額 10^8 円に
  対して 1e-4 円未満であり、**円単位の丸め幅（0.5 円）より 3 桁以上小さい**
- **精度以外の入力誤差のほうが支配的。** 暗号資産の入出庫は現在価格での仮評価、candle 欠落時は
  現在価格へのフォールバックという近似が既に入っている。ここに厳密有理数を持ち込んでも、
  出力の正しさは 1 円も改善しない

加えて実務上の理由として、ADR-005 の性能計測（同 ADR の表）が示すとおり非丸めの有理数は
分母が構造的に肥大する。日次グリッド × 全時点の再構築は約定件数 × グリッド点数の演算になるため、
有理数では現実的な応答時間に収まらない。

**この決定は税務経路には一切及ばない。** `cli/tax/` は引き続き ADR-005 に従う。

### なぜブロックせず申告に留めるのか

`cli/tax/guard/reference-pnl.ts` は履歴の打ち切りを**独立したブロック条件**にしている
（[ADR-006](006-reference-pnl-guard-scope.md)）。これは「証明可能性が要る」税務だからで、
残高推移には同じ強度は要らない。**打ち切った窓の系列にも観察価値はある**（直近 30 日だけ見たい、
特定銘柄の値動きの影響を見たい）ので、数値を出さないより「欠けている」と明示して出すほうが有用。

ただし**黙って通すのは禁止**とし、3 段で申告する:
`Result.partial` / `meta.truncated`（envelope）、`data.completeness`（構造化）、
`data.warnings`（人が読む文）。envelope を読まない経路でも欠落に気づけるようにするため重複させる。

## 検討した代替案

| 案 | 判定 |
|---|---|
| skill 側で CLI の生データを組み合わせて復元させる | 却下。上記「生データを渡しても復元できない」。誤りが静かで検証もできない |
| MCP を import して再利用する | 却下。CLAUDE.md / [ADR-001](001-cli-vs-mcp-separation.md) が別リポの直接 import を禁じている |
| 厳密有理数（ADR-005 を全面適用） | 却下。丸めが意味を持つ要件が無く、誤差は丸め幅より 3 桁以上小さい。性能面でも成立しない |
| 打ち切り時はエラーにする（tax と同じ強度） | 却下。窓を狭めた観察が正当な用途であり、申告付きで出すほうが有用 |

## 影響

- `cli/portfolio/`（復元・評価・純入出金・注記）と `cli/commands/private/balance-history.ts` を追加。
  ADR-002 の「影響」節に本 ADR への参照を追記した
- `cli/tax/import/paginate.ts` を `cli/paginate.ts` へ移した。「短いページを最終ページと見なさない」
  停止条件は税務固有ではなく、**履歴が 1 件欠けたら集計が狂う用途すべて**に必要なため。
  private コマンドが tax（例外カテゴリ）配下へ依存する形を避ける狙いもある。
  あわせて**同一タイムスタンプの行が 1 ページ上限を超えた場合**（カーソルが進まず同じ満杯ページが
  返り続ける）を完了扱いにせず `truncated` で返すようにした。満杯かどうかは要求 `count` と、
  「後続ページで新規行が来た = 直前ページは最終ページではなかった」から逆算した実測上限の
  両方で判定する。**残る穴**: 走査の最初から全行が同一タイムスタンプで、かつサーバが `count` を
  クランプする場合は上限を観測できないため検出できない（tax 経路も同じ）
- **同じ復元ロジックが CLI と MCP の 2 か所に存在する。** 片方だけ直すと静かに食い違うので、
  各ファイル冒頭に移植元（`ecf05ae` 時点のパス）を明記した
- **移植元との意図的な差分が 4 点ある**（いずれも本文中にコメントを残した）:
  1. 現在残高に `withdrawing_amount` を足し戻す（出金申請中は onhand から引かれているが、
     巻き戻しでは status=DONE の出庫しか戻さないため。`cli/tax/import/fetch-assets.ts` と同じ定義）
  2. `confirmed_at` を欠く DONE 入庫は `found_at` へフォールバックする（移植元は `confirmed_at`
     固定。欠落レコードを落とすと再構築が静かに狂うため）
  3. グリッドは **UTC 日境界**（移植元は JST）。CLI は「JST は表示用のみ」が規約で、税務
     （ADR-004）以外では持ち込まない
  4. **売りの巻き戻しでも base 建て手数料を戻す**（移植元は買いだけ）。本 CLI の理論残高再構築
     `cli/tax/reconcile/rebuild.ts#applyTrade`（独立実装との突合で残差一致を確認済み）は
     買い・売りの両方で base 手数料を base から引いており、そちらへ揃えた。実口座では
     `fee_amount_base` が全行ゼロ（`docs/dev/tax-evidence/ANSWERS.md` §1）なので現状の出力は
     変わらないが、非ゼロが来たときに静かにずれない側へ倒す
- **信用約定は巻き戻さない**（`position_side` の有無で除外。tax 経路の spot / margin 分離と同じ判断）。
  現物残高を動かさないので現物と同じ式では巻き戻せない一方、**実現損益は JPY 残高を動かす**ため、
  期間内に信用決済がある口座では過去の点がその分ずれる。除外したことと影響を `warnings` と
  `assumptions` に出す。信用を含めた復元は本 PR のスコープ外（宿題）
- 残る宿題: `--year` 相当の期間指定（系列は現在評価額で終端する前提なので、過去年だけを切り出す
  には最終点の扱いを決める必要がある）。skill 側の書き換えは後続 PR
