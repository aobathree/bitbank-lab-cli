# ADR-005: 税務計算の内部数値は厳密有理数とし、丸めは厳密値に一度だけ適用する

## ステータス

Accepted（2026-07-25）

## コンテキスト

税務計算（[ADR-004](004-tax-logic-in-cli-exception.md) の `tax` カテゴリ）の数値要件は
[tax-research.md](../dev/tax-research.md) P-02 と [tax-requirements.md](../dev/tax-requirements.md) §7:

- 全金額・数量は文字列 → Decimal 直パース。**浮動小数点禁止**
- 内部は**非丸め**。丸めは (i) 出力層と (ii) 国税庁 Excel 互換モード（`NTA_SHEET_2025_12`）に隔離
- 不変条件 **I1: `期首簿価 + Σ取得価額 == Σ譲渡原価 + 期末簿価`（厳密一致）** を必須テストにする

JS の `number` は IEEE754 なので使えない。残る選択は「有効桁を持つ十進ライブラリ
（decimal.js 等）」か「厳密有理数」か。

### 問題の本質は精度ではなく「丸めの適用回数と適用対象」

有効桁を増やしても解決しない。簿価 100 円・数量 6 から 3 単位を売却する場合:

```text
単価 = 100 / 6 = 16.6666…（無限小数）
売却後残高価額 = 単価 × 3 = 50   ← 厳密には割り切れて整数
```

互換モード（付録D.3）は売却の都度 `ROUNDUP(単価 × 残高数量)` を評価する。ここで
**単価を先に十進で確定させてから乗算すると**、`prec=50` でも:

```text
単価' = 16.66666666666666666666666666666666666666666666666667  (50 桁)
単価' × 3 = 50.00000000000000000000000000000000000000000000000001
ROUNDUP(…) = 51   ← 誤り（正しくは 50）
```

桁を増やしても最後の桁に必ず誤差が残るため、**丸め境界にちょうど乗るケースは何桁でも
再現する**。同じ理由で I1 も厳密一致しない（`E×F + E×H ≠ B+D`）。

つまり必要なのは「もっと多い桁」ではなく、**丸めを厳密値に対して一度だけ適用すること**である。

## 決定

1. **設計原則（本 ADR の中核）**:
   **丸めは常に厳密値に対して 1 回だけ適用する。丸め済みの中間値に再度丸めを適用しない。**
   - 互換モードの `ROUNDUP` / `ROUNDDOWN` は、単価を先に確定させてから乗算するのではなく、
     `ceil(cost × R / Q)` のように**厳密値に対する単一操作**として評価する
   - 丸めの出口はコード上 1 箇所（`cli/tax/ratio-decimal.ts` の `roundAtScale`）に限定し、
     エンジン内の四則演算は一切丸めない
2. **上記原則を成立させる手段として、内部表現に厳密有理数を採る**（`{ n: bigint, d: bigint }`、
   常に既約・`d > 0`）。有理数は手段であり目的ではない
3. **外部依存は追加しない**（BigInt はランタイム標準）。CLAUDE.md「外部依存最小」と整合
4. **汎用の数値タワーは作らない**。実装するのは加減乗除・gcd 約分・指定丸めでの整数化・
   decimal レンダリングのみ
5. **有理数はエンジン内部に閉じ込める**。入出力境界（API 生値・永続化・レポート・JSON 出力）は
   十進文字列に固定する（境界の規則は下記「レンダリング規則」）

## 検討した代替案

| 案 | I1 厳密一致 | 互換モードの丸め境界 | 外部依存 | 判定 |
|---|---|---|---|---|
| **厳密有理数（採用）** | ○ 恒等的に成立 | ○ 厳密値に 1 回だけ丸めるので正しい | なし | 採用 |
| decimal.js（有効桁 20〜50） | × 許容誤差が必要 | **× 上例のとおり桁を増やしても 51 になる** | 追加 1 本 | 却下 |
| 差引方式（`cogs = (B+D) − closing_cost`） | ○ 定義上成立 | **× 解決しない**（別問題） | なし | 併用（下記） |

**差引方式について**: これは代替案ではない。[tax-research.md](../dev/tax-research.md) §3 の
擬似コードが既に `cogs = (opening.cost + acq.cost) − closing_cost` を採用しており、
**現行仕様そのもの**である（付録D.2 の `G = E×F` は国税庁 Excel シート側の数式であり、
互換モードで再現する対象。E が非丸めである限り両者は数学的に一致する）。差引方式は I1 を
定義上成立させるが、互換モードの `ROUNDUP` 境界問題は解決しないため単独の解にはならない。
本 ADR の有理数採用と併用する。

## レンダリング規則（内部 ⇄ 境界）

| 境界 | 表現 | 規則 |
|---|---|---|
| API 生値の取込 | 十進文字列 → 有理数 | `fromDecimalString`。float を一切経由しない（`Number()` 禁止） |
| エンジン内部 | 有理数 | 丸めない。演算ごとに gcd 約分 |
| 数量の出力 | 十進文字列 | scale 8（bitbank の最大 `amount_digits`）・`ROUNDDOWN`。付記: 元が 8 桁を超える入庫は保留リストへ |
| 金額（円）の出力 | 十進文字列 | 既定 scale 0・`ROUNDDOWN`（円未満切捨て表示）。内部値は別途保持し、丸め前後の両方をレポートに出す |
| 手数料の出力 | 十進文字列 | scale 4（付録E.1 の API 丸め桁に合わせる。P-16） |
| 参考損益の出力 | 十進文字列 | 負値のまま出す（v2 §9）。scale 0・`ROUNDDOWN` は絶対値ではなく数値に対して適用し、規則をレポートに明記 |
| 互換モード | 整数（円） | 総平均法: 収入計 `ROUNDDOWN` / 経費計 `ROUNDUP` を**集計後の厳密値に 1 回**。移動平均法: 売却の都度 `ROUNDUP(cost × R / Q)` を**厳密値に 1 回** |
| 繰越（互換 DISPLAY） | 整数（円） | `HALF_UP`（付録D.5 の表示値転記の再現）。`EXACT` は非丸めのまま |

`ROUNDDOWN` / `ROUNDUP` は Excel 準拠で**ゼロ方向切捨て / ゼロから離れる方向切上げ**として
実装する（非負値では floor / ceil と一致するが、負値で挙動が異なるため明示的に分ける）。

## 影響

- **本 ADR は税務経路（`cli/tax/`）に閉じた規約であり、CLI 全体の規約ではない。**
  [ADR-007](007-balance-history-reconstruction-in-cli.md) は残高推移の再構築について、
  丸めが意味を持つ要件（I1 の厳密一致・互換モードの丸め境界）が無いことを理由に
  倍精度を採っている。本 ADR の適用範囲を広げる判断はしていない
- `cli/tax/ratio.ts`（四則・比較・約分）と `cli/tax/ratio-decimal.ts`（パース・丸め・
  レンダリング）を追加。丸めはこの 1 箇所だけが行う
- **検証**: (i) 丸め境界テスト（単価が無限小数かつ単価×数量が整数になるケースで `ROUNDUP` が
  切上げないこと）、(ii) Python `fractions.Fraction` で生成した期待値との突合プロパティテスト
  （`cli/__tests__/__fixtures__/tax/ratio-reference.ts`、生成器は `scripts/dev/gen-ratio-reference.py`）
- 実データでのベンチマークは `fixtures/`（実口座データ）が本リポジトリに入った時点で実施する。
  丸い数値の合成データは gcd 約分が効きすぎて分母が肥大せず、計測が楽観的になるため代替にならない

## 性能計測の結果（2026-07-26 再計測・合成データ・`scripts/dev/bench-ratio.ts`）

移動平均法で計測（売却のたびに分母が数量を取り込むため総平均法より重い）。
`realistic` = 定型ロット（0.00001〜0.001）の反復、`worst` = 8 桁がバラバラな数量。
いずれも合成データであり、**実データでの確定値は fixtures 投入後に再計測する**。

> **初版（2026-07-25）からの再計測**: 生成器が保有残高を超える売却を出しており、
> 残高が負に振れる**台帳として成立しない系列**を計測していた。売却数量を保有で
> 上限化して測り直した数値が下表。**結論は変わらない**（非丸め経路は 10^5 件に届かない）が、
> 打切り点・bit 増加率が動いたため差し替えた。

| 経路 | 1,000 件 | 3,000 件 | 5,000 件 | 100,000 件 | 分母 bit 長 |
|---|---|---|---|---|---|
| realistic / 非丸め（既定） | 133 ms / 1,416 bit | 4.7 s / 4,397 bit | 29.6 s / 7,619 bit | **60 s で 5,978 件で打切り**（8,928 bit） | 約 **+3.8 bit/売却** で線形増加 |
| worst / 非丸め（既定） | 2.3 s / 5,006 bit | 打切り（2,549 件） | 打切り | 打切り | 約 **+13 bit/売却** |
| realistic / 互換（売却毎 ROUNDUP） | 3 ms | 9 ms | 12 ms | **262 ms** | **≤ 17 bit（有界）** |
| worst / 互換（売却毎 ROUNDUP） | 3 ms | 11 ms | — | **334 ms** | **≤ 27 bit（有界）** |

**分母肥大は構造的**: 移動平均法の売却は `cost' = cost × (Q−q)/Q` であり、分母に毎回 Q の
分子（8 桁数量なので最大 10^9 ≒ 30 bit）が乗る。gcd 約分が大半を打ち消しても純増
約 3.8 bit/売却（数量が 8 桁バラバラだと約 13 bit/売却）が残り、BigInt 演算コストが
bit 長の二乗で効くため所要時間は超線形に伸びる。
**非丸めの移動平均法は 5,000 件程度が実用上限**で、NFR（10^5 件）を満たせない。
一方、互換モードは売却の都度 `ROUNDUP` で簿価が整数に戻るため分母が有界で、10^5 件が 0.3 秒。

### 「閾値超で再正規化」の要否 → **行わない**

再正規化（bit 長が閾値を超えたら簿価を所定桁で丸め直す）は分母を有界化できるが、
**丸め済みの中間値に再度丸めを適用する**ことになり本 ADR の中核原則に反する。
誤差が売却ごとに累積し、互換モードの `ROUNDUP` 境界問題も再発する。したがって再正規化は採らず、
**経路を分ける**（下記）。

### 推奨（要確認・仕様レベルの判断を含む）

- **総平均法（法定評価方法・既定）**: 完全に厳密。除算は通貨・年あたり 1 回のみで
  10^5 件でも即時。**このまま非丸めを既定にする**（問題なし）
- **移動平均法**: 次の 2 経路に分ける
  1. `NTA_SHEET_2025_12` 互換（売却の都度、厳密値に 1 回 `ROUNDUP`）— 高速・有界。
     国税庁計算書が実際に行っている計算そのもの（付録D.3）であり、精度の妥協ではなく
     参照実装への忠実性
  2. 完全非丸め — 厳密だが件数制限付き。既定件数上限（暫定 5,000 件）を超えたら
     **黙って劣化させず明示エラー**にし、互換経路か総平均法を案内する
- **未解決の仕様論点**: v2 付録D.6 は「既定は P-02（内部非丸め）、互換モードは
  レポートの参照列と回帰テストにのみ使用」と定めている。上記推奨は
  **移動平均法の実用既定を互換側に寄せる**ため D.6 と衝突する。仕様側の判断が必要
  （税務監修の対象にもなり得る）。判断が出るまで実装は 2 経路を両方用意し、
  既定は D.6 どおり非丸め＋件数上限とする
