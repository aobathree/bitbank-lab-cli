# ADR-006: 参考損益の表示ガードが守る範囲と、対象外にする唯一の例外

## ステータス

Accepted（2026-07-28）

## コンテキスト

[ADR-004](004-tax-logic-in-cli-exception.md) で CLI 内に置いた税務計算の安全装置の中核が、
参考損益の表示ガード（`cli/tax/guard/reference-pnl.ts` の `evaluateGuard`）である。
銘柄ごとに (a) アテステーション / (b) 取得価額を未確定にするフラグの不在 / (c) 前年繰越の確定 /
(d) 残高突合の一致 / 履歴が打ち切られていないこと、をすべて満たしたときだけ参考損益を
**数値で**出し、満たさなければ欄そのものを出さずに `blocked_by` へ理由を並べる。

コードレビュー（2026-07-27）で「ガードを迂回して損益数値が出る経路がないか」を検査した。
結果は次のとおり:

- `tax pnl` の `currencies[].reference` と `nta_compat` は `report/currency.ts` が
  必ず `evaluateGuard` を通しており、迂回する経路は存在しない
- ただし `tax verify-report` の信用行（`margin_pnl`）だけは `evaluateGuard` を通さずに
  **銘柄別・年別の損益数値**を出す。全出力の中でこれが唯一

この 1 箇所が「意図した設計」なのか「見落とし」なのかが、コードにもドキュメントにも
書かれていなかった。このままでは次のレビューで同じ疑いが再燃するか、あるいは
親切心でガード配下へ "修正" され、verify-report の突合機能そのものが壊れる。

判断には「そもそもガードは何を守る装置なのか」の定義が要るが、それも明文化されていない。

## 決定

1. **ガードの保護対象を「取得価額の確定性に依存して初めて意味を持つ数値」と定義する。**
   具体的には現物の参考損益（`currencies[].reference.*`）と国税庁計算書互換値
   （`currencies[].nta_compat`）。いずれも CLI が平均法で計算した値であり、前提
   （口座外の同一銘柄・未解決の入庫・前年繰越・残高突合・履歴の完全性）が 1 つでも崩れると
   誤った数値になる
2. **`tax verify-report` の信用損益（`margin_pnl`）はガード対象外とする。** これは
   ガード外で損益数値が出る唯一の箇所であり、迂回ではなく意図的な例外である
3. 新しい出力を足すときは 1 の定義に当てはまるかで判断する。当てはまるならガード配下に置く。
   当てはまらないと判断してガード外に出すなら、**本 ADR に例外として追記する**
   （現時点の例外は 2 の 1 件のみ）

## 理由

- **`margin_pnl` は CLI 独自の所得計算ではない。** 突合の両辺とも bitbank 自身が既に
  出している実現値である（報告書側 = 年間取引報告書「年中信用取引損益」、API 側 =
  約定履歴の `profit_loss`）。CLI がやるのは、報告書の定義（値幅損益 − 利息。手数料は
  控除しない）へ揃えるために API 側の手数料を足し戻す加減算だけで、**取得価額の推定を
  一切しない**。ガードが防ぎたい「前提が崩れた状態で CLI が推定した数値」に当たらない
- **信用の実現損益は取得価額計算に依存しない別系統。** 信用は個別法（FIFO）で建玉ごとに
  損益が確定し、現物の総平均法・移動平均法の簿価とは無関係。ガードの (b) 未解決入庫や
  (c) 前年繰越は、信用の実現損益の正しさに何も影響しない。ガード配下へ置くと
  **無関係な条件で突合が塞がれる**
- **ガードと verify-report は目的が逆を向いている。** ガードは「前提が崩れているときに
  数値を出さない」装置。verify-report は「報告書と API が食い違っていることを検出する」
  装置で、食い違いこそが成果物である。ガードを掛けると、差が出ている（＝最も見たい）
  状況ほど数値が消える
- **ガードを外しても fail-closed の実質は失われない。** verify-report は差を診断
  （`MATCH` / `FEE_ROUNDING` / `REPORT_EXCESS` / `API_EXCESS`）と許容幅つきで出し、
  集計から除外した件数（非 JPY クォート・`realized_net` 欠損）や履歴打ち切りを
  `warnings` に出す。数値を黙って正しいものとして提示する経路ではない
- **そもそも出力の性質が違う。** verify-report が出すのは突合結果であり、`tax pnl` の
  「参考損益」ではない。両者を同じガードで括ると、名前も意味も違う 2 つの数値に
  同じ前提条件を課すことになる

## 影響

- `cli/tax/verify/margin-aggregate.ts` の冒頭に「`evaluateGuard` を通らないのは意図的」と
  本 ADR への参照を書く。ガード配下へ移す変更は本 ADR の再検討を伴う
- `cli/tax/guard/reference-pnl.ts` の `GuardInput` は、フィールドごとに渡すべき集計スコープが
  違う（フラグ検査と `deferred` は**当年**、`reconciliation`・`truncated`・
  `carryoverZeroRejected` は**全履歴**）。型定義の doc コメントに契約として明記する。
  組み立ては `report/build.ts` の 1 箇所だけ
- 非 JPY クォート（BTC 建て等）の約定が**過去に 1 度でも**ある通貨は、残高突合が全履歴で
  行われる以上 (d) が**以後の全年度で**成立せず、参考損益が恒久的に出ない。交換取引の
  完全計算（P1）が入るまで解けない。fail-closed として正しい挙動だが、ユーザーからは
  「なぜこの銘柄だけずっと出ないのか」が見えないため、`skills/tax-report/SKILL.md` の
  Gotchas で不具合ではないことを説明する
- 本 ADR は挙動を変えない。既存の出力・テスト期待値はそのまま

### 追記（2026-08-14）: `--carryover=zero` の反証は (b) の年スコープとは別軸

上の「フラグ検査は**当年**」は維持する。前年に未解決入庫があっても、当年の繰越ファイルを
正しく渡した人まで止めるのは (c) の仕事であって (b) の仕事ではない、という切り分けは変えない。

ただし `--carryover=zero`（当年が初年度）だけは、**ユーザーの主張であると同時に CLI が
全履歴で反証できる事実主張**である。前年以前に同一銘柄のイベントがあれば初年度ではないので、
`report/run.ts` はその銘柄をゼロ確定の繰越として埋めず、(c) が理由付きで止める
（`GuardInput.carryoverZeroRejected`）。

これを入れないと次の穴が残る: 前年に入庫のみ・当年は板で売買した銘柄は、当年イベントに
ブロックフラグが立たず（(b) は当年スコープ）、残高突合も入庫を数量に含めたまま MATCH するため、
**入庫分を母集団から落とした平均単価**が (a)〜(d) をすべて通過して数値で出る。

明示の `--carryover` ファイルは従来どおり通す。ファイルの中身が正しいかは機械では反証できず、
それを受けることが (c) の意味そのものだからである（B案の限界）。
